COMO INSTALAR O TOOLBOX45 A PARTIR DO GITHUB
================================================

Repositório: https://github.com/seg45/toolbox45
Servidor: Linux (Ubuntu/Debian), com acesso root/sudo, Docker + Docker Compose.

A aplicação roda como 3 containers Docker (ver docker-compose.yml):
  - toolbox45-db        PostgreSQL (banco de dados)
  - toolbox45-backend   API REST (Python/FastAPI)
  - toolbox45-frontend  nginx (frontend React — build estático — + proxy reverso de /api/*)

Só o toolbox45-frontend tem porta publicada no host — é com ele que o
navegador fala; toolbox45-backend e toolbox45-db não são alcançáveis de
fora do host. Não há mais instalação bare-metal (systemd) — esta versão
depende de um servidor Postgres próprio, então Docker Compose é o único
caminho suportado.


1) PRÉ-REQUISITOS
------------------
- Acesso root ou sudo no servidor.
- git instalado (se não tiver: sudo apt-get install -y git).
- Docker + Docker Compose (se não tiver: sudo apt-get install -y docker.io docker-compose-plugin).


2) CLONAR O REPOSITÓRIO
------------------------
Evite clonar dentro do home de um usuário (ex.: /home/usuario/...) — prefira
um local neutro, como /opt:

    sudo git clone https://github.com/seg45/toolbox45.git /opt/toolbox45
    cd /opt/toolbox45

Se o git reclamar de "dubious ownership", rode:

    git config --global --add safe.directory /opt/toolbox45


3) INSTALAR (subir os 3 containers)
--------------------------------------
    sudo docker compose up -d --build

Isso constrói as imagens do backend e do frontend (o frontend é compilado
dentro do próprio build — não precisa de Node instalado no servidor), baixa
a imagem oficial do PostgreSQL, e sobe os 3 containers. O build do frontend
consome bastante memória: em servidores pequenos (~1 GB de RAM) configure
swap antes (ver "Problemas comuns", no fim deste arquivo). O app fica
disponível em:

    https://<ip-do-servidor>         (porta 443 — toolbox45-frontend)

A porta 80 só REDIRECIONA para HTTPS (exceto GET /api/health, usado em
healthchecks): o cookie de sessão é marcado "Secure" e só trafega por HTTPS.
No primeiro acesso o navegador avisa do certificado autoassinado (ver
passo 6). Se um dia houver um proxy na frente que termine o TLS e fale HTTP
com este nginx, remova o redirect da porta 80 em frontend-react/nginx.conf
(senão dá loop) e repasse o cabeçalho X-Forwarded-Proto: https.

Numa instalação NOVA: não precisa fazer mais nada. No primeiro boot o
backend aplica o schema e semeia sozinho (só onde a tabela está vazia):

  - o usuário local admin / admin (role super_admin) — TROQUE A SENHA assim
    que entrar (Configurações → Account, ou Settings → Users);
  - a pasta "Favorites" de cada usuário;
  - o catálogo base: fornecedores (Check Point, Fortinet), sistemas,
    versões, ambientes, parâmetros de busca, prompts e templates de export.

NENHUM comando vem pré-cadastrado, e a lista de Tópicos começa vazia: crie os
tópicos em Configurações → Register → Topics e cadastre os comandos pela
própria aplicação (editor de comandos) ou importe em lote por CSV
(Configurações → Database → Commands → Import; o modelo do CSV está na
própria janela de importação e em import-templates/).

(O antigo "node seed.js", que carregava ~30 comandos de referência, foi
removido junto com o backend Node — já não funcionava com o schema atual.)


4) VARIÁVEIS DE AMBIENTE (opcional)
--------------------------------------
Definidas num arquivo ".env" ao lado do docker-compose.yml, ou exportadas
antes do "docker compose up". IMPORTANTE: este repositório é PÚBLICO no
GitHub — o .env NUNCA deve ser adicionado ao git (já está no .gitignore);
só existe localmente no servidor.

    POSTGRES_DB / POSTGRES_USER / POSTGRES_PASSWORD
        # credenciais do banco (usadas por toolbox45-db E toolbox45-backend
        # — mudar aqui já reflete nos dois). Troque a senha padrão em
        # produção.

    GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET / GOOGLE_REDIRECT_URI
        # opcional — habilita o botão "Sign in with Google" em login.html
        # (ver docs/api.md e docs/server-overview.md para o passo a passo
        # completo de criar o Client ID/Secret no Google Cloud Console).
        # GOOGLE_REDIRECT_URI precisa ser a URL pública exata de
        # GET /api/auth/google/callback (ex.:
        # https://toolbox.seg45.com.br/api/auth/google/callback),
        # registrada nos "Authorized redirect URIs" do Client ID. Sem as 3
        # variáveis, o botão fica escondido — nunca trava a aplicação.

    MICROSOFT_CLIENT_ID / MICROSOFT_CLIENT_SECRET / MICROSOFT_REDIRECT_URI
    MICROSOFT_TENANT_ID (opcional, padrão "common")
        # opcional — mesmo esquema do Google, com o botão "Sign in with
        # Microsoft" (passo a passo no Azure Portal em
        # docs/server-overview.md).

    Observação: Google e Microsoft também podem ser configurados pela própria
    UI (Configurações → System → OAuth); o valor salvo na UI tem precedência
    sobre estas variáveis.

Depois de mudar variáveis, recrie os containers:

    sudo docker compose up -d --build


5) API KEYS (acesso programático externo)
----------------------------------------------
Scripts/integrações externas podem chamar a API enviando um header
`X-API-Key` — isso pula a sessão/login inteiramente. Crie/revogue chaves
pela própria aplicação, em Configurações → System → "API access", ou
direto:

    curl -X POST http://<ip-do-servidor>/api/api-keys \
      -H "Content-Type: application/json" -d '{"name": "minha integração"}'

A key completa só aparece nessa resposta (uma vez) — guarde-a com cuidado;
depois disso só o hash fica no banco.


6) HTTPS COM CERTIFICADO
---------------------------------------
HTTPS já vem habilitado por padrão, sem nenhum passo manual: no primeiro
boot, o toolbox45-backend gera automaticamente um certificado autoassinado
(ensure_tls_bootstrap(), ver server-py/app/tls.py) e o grava num volume Docker
compartilhado ("toolbox45-tls") com o toolbox45-frontend, que o serve em
https://<ip-do-servidor> (porta 443); a porta 80 apenas redireciona para ele.
O nginx também envia cabeçalhos de segurança (CSP, HSTS de 30 dias, etc.) e
limita a taxa de login (~6/min por IP), de cadastro (~3/min) e da API.
O navegador vai mostrar aviso de segurança enquanto o certificado for
autoassinado — normal.

Para trocar por um certificado de verdade (CA da empresa ou Let's Encrypt),
não é mais preciso mexer em arquivo nenhum no servidor: use a própria UI,
em Configurações → System → SSL Certificate → "Manage certificate" (só
admin). Cole (ou envie o arquivo) do certificado e da chave privada em PEM
(sem senha) — um "chain"/intermediários é opcional — e clique em "Save
certificate". Em poucos segundos o nginx do frontend recarrega sozinho com
o novo certificado (um watcher com inotifywait dentro do container dele —
ver frontend-react/docker-entrypoint.sh — detecta a mudança no volume
compartilhado e dá "nginx -s reload"), sem reiniciar nenhum container e sem
derrubar conexões em andamento.

O botão "Remove custom certificate" na mesma tela reverte para um
autoassinado novo, a qualquer momento.


7) BACKUP & RESTORE
------------------------
Pela própria aplicação (Configurações → Database → "Backup &
Restore"): cria um dump do Postgres (`pg_dump`, formato custom) guardado no
volume "toolbox45-backups" (fora do container, sobrevive a rebuild).
Também dá pra agendar backups automáticos (diário/semanal/mensal) na mesma
tela.

Backup manual via linha de comando (equivalente ao botão da UI):

    sudo docker compose exec toolbox45-backend \
      pg_dump -d "postgresql://toolbox45:toolbox45@toolbox45-db:5432/toolbox45" -F c -f /app/backups/manual.dump

Para restaurar um dump trazido de outra instalação, copie o arquivo .dump
para dentro do volume e restaure pela UI (Backup & Restore → Restore), ou:

    sudo docker cp meu-backup.dump $(docker compose ps -q toolbox45-backend):/app/backups/meu-backup.dump
    sudo docker compose exec toolbox45-backend \
      pg_restore --clean --if-exists --no-owner -d "postgresql://toolbox45:toolbox45@toolbox45-db:5432/toolbox45" /app/backups/meu-backup.dump


8) VERIFICAR A INSTALAÇÃO
------------------------------
    sudo docker compose ps
    sudo docker compose logs -f toolbox45-backend    # deve mostrar "schema aplicado" e "Uvicorn running"
    curl -I http://localhost


9) ATUALIZAR DEPOIS
------------------------
Dentro da pasta do projeto:

    git pull
    sudo docker compose up -d --build

É seguro rodar quantas vezes precisar — reconstrói só o que mudou e nunca
mexe nos dados (volumes toolbox45-db-data e toolbox45-backups continuam
intactos entre updates).


10) COMANDOS DO DIA A DIA
------------------------------
    sudo docker compose logs -f toolbox45-backend    # acompanhar logs do backend
    sudo docker compose logs -f toolbox45-frontend    # acompanhar logs do nginx
    sudo docker compose restart toolbox45-backend     # reiniciar só o backend
    sudo docker compose down                           # parar tudo (mantém os volumes/dados)
    sudo docker compose down -v                         # parar E apagar os volumes (perde os dados!)


11) BUILD TRAVA EM "apt-get update" (Connection timed out)
--------------------------------------------------------------
Sintoma: o build para na etapa de dependências do backend (ver
server-py/Dockerfile) ou do frontend, baixando pacotes Debian/Alpine/npm, com "Get:1 ... InRelease" repetindo várias vezes e
terminando em "Connection timed out", mesmo o host tendo internet normal
(curl/apt do host funcionam sem problema).

Causa provável: PMTU black hole — algum ponto do caminho de rede (VPN,
firewall, certas redes de nuvem) descarta os pacotes ICMP "fragmentação
necessária", então pacotes pequenos (handshake TCP, respostas HTTP/TLS
pequenas) passam, mas qualquer transferência que precise de um pacote no
tamanho máximo (MTU cheio) trava pra sempre. Isso afeta tanto HTTP quanto
HTTPS, e afeta o host inteiro, não só o Docker — então a correção é no
host, com um "clamp" do MSS do TCP:

    # 1) confirmar o diagnóstico (opcional): estas duas linhas devem travar
    #    (ou demorar até o timeout) se for isso mesmo:
    curl -m 8 -o /dev/null -s -w "HTTP:  %{http_code}  %{time_total}s\n" http://deb.debian.org/debian/dists/bookworm/InRelease
    curl -m 8 -o /dev/null -s -w "HTTPS: %{http_code}  %{time_total}s\n" https://deb.debian.org/debian/dists/bookworm/InRelease

    # 2) aplicar o clamp (efeito imediato, não precisa reiniciar nada)
    sudo iptables -t mangle -A OUTPUT -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --set-mss 1400

    # 3) confirmar que resolveu (repita o teste do passo 1 — agora deve
    #    responder rápido, "200", em bem menos de 1 segundo)

    # 4) tornar permanente (a regra acima não sobrevive a reboot por si só)
    sudo apt-get install -y iptables-persistent   # ou netfilter-persistent
    sudo netfilter-persistent save

Se 1400 não resolver, teste valores menores (1300, 1200) — o valor ideal
depende de quanto overhead a rede/VPN em questão está adicionando. Tanto o
serviço toolbox45-backend quanto o toolbox45-frontend já usam
"network: host" no build (ver docker-compose.yml) por causa disso.


12) PROBLEMAS COMUNS
------------------------
- "toolbox45-backend" reiniciando em loop, log mostra "[db] Falha ao
  conectar/aplicar schema (tentativa N/30)": o toolbox45-db ainda pode estar
  inicializando (primeira vez que o volume é criado, o Postgres oficial
  demora alguns segundos) — o backend tenta reconectar por ~1 minuto
  sozinho (ver server-py/app/db.py); se persistir depois disso, confira
  "docker compose logs toolbox45-db" e se POSTGRES_USER/POSTGRES_PASSWORD
  do .env batem com os do volume já criado.

- Build do frontend morre sem mensagem clara (ou o servidor fica
  irresponsivo durante o "docker compose up -d --build"): falta de memória
  — o build do frontend (npm + tsc + vite) tem um pico de memória alto; num
  servidor de ~1 GB de RAM (caso do docker01 da SEG45) foi necessário um
  swap de 1 GB para o build concluir. Crie o swap antes de buildar:
      sudo fallocate -l 1G /swapfile && sudo chmod 600 /swapfile
      sudo mkswap /swapfile && sudo swapon /swapfile
      echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
  Confirme com "free -m" e "dmesg | grep -i oom".
  No docker01 o swap hoje é de 2 GB (dois arquivos de 1 GB: /swapfile e
  /swapfile2) com vm.swappiness=10 (/etc/sysctl.d/99-toolbox45.conf). Para
  o banco e o backend nao serem mortos pelo kernel quando um build estoura
  a RAM, o docker-compose.yml define oom_score_adj: -500 nos dois, e o
  Dockerfile do frontend limita o heap do Node no build
  (NODE_OPTIONS=--max-old-space-size=384). Para ver se houve OOM:
      sudo journalctl -k --since "7 days ago" | grep -i -E "out of memory|oom-kill"

- Login não funciona / usuário não consegue entrar: o Toolbox45 só aceita
  login local (usuário/senha, Settings → Users) ou login com
  Google (se GOOGLE_CLIENT_ID/SECRET/REDIRECT_URI estiverem configurados —
  ver seção 4 acima e docs/server-overview.md); não existe mais login
  automático do Windows (NTLM, removido). Para acesso programático, use uma
  API key (seção 5 acima) em vez de tentar autenticar como um usuário do
  navegador.

- Ver logs detalhados de um container específico:
      sudo docker compose logs -f toolbox45-backend
      sudo docker compose logs -f toolbox45-db
      sudo docker compose logs -f toolbox45-frontend
